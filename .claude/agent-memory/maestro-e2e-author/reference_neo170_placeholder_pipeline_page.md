# /placeholders run view (NEO-170) — selectors & the resolverCalls gotcha

Page: `apps/web/app/placeholders/page.tsx`. E2E entry seeds via
`/testing/seed-placeholder-upload` (STREAM mode) which redirects to
`/placeholders?jobId=…`. The run view is `page.tsx` (h1 "Placeholder Scans").

## Visible strings (verified vs source, do not guess)
- Status line = `jobSummary`: `"<Status> — <done> of <total> images processed, <failed> failed, <pairCount> pairs"`. `<Status>` is `statusLabel(job.status)` = the status capitalized: `Collecting` / `Pairing` / `Processing` / **`Succeeded`** / `Failed`. So a finished stream reads `"Succeeded — 6 of 6 images processed, 0 failed, 3 pairs"` (the dash is an em dash — bridge it with `.*`, never match it literally).
- `"resolver calls: <n>"` — its own `<p>`, always rendered when a job exists. Assert exactly.
- Session panel buttons (rendered only while status ∈ pending/uploaded/collecting/extracting/processing/pairing — i.e. `canAct`): **`Close Session`** and **`Abort Session`**. Both DISAPPEAR once the job reaches a terminal status.
- Pair line: `"<name> · #<num> · <confidence> · <mechanism>"` where mechanism = "by image pool" (pool) | "by scan order" (adjacency fallback). **DO NOT assert the mechanism OR confidence OR name — ALL are non-deterministic** (they depend on a real vision model OCR-ing invented names off synthetic cards; CI run 32282476481 proved it: VORKLE fell to "by scan order" while QUILLDEN/MOSSBAUM matched "by image pool", same fixtures). Pool-vs-fallback matching is owned by the ~50 deterministic `convex/lib/pairing/pool.test.ts` unit tests, NOT the E2E. The E2E asserts only DETERMINISTIC outcomes: "6 of 6 … 3 pairs", Close→"Succeeded", "resolver calls: 6" (proves identity-first RAN over all 6; 0 under the old adjacency pre-pass), and the 3 card numbers.
- **Asserting a pair by card number — the disambiguator.** The card number (#17/#42/#83, large/high-contrast → OCRs reliably) appears in BOTH the pair row AND the Images-section back summary. On the pair row the number is mid-line (`… · #17 · <confidence> · <mechanism>`); in the image summary (`Done — back side · <name> · #17`) it is the LAST token. So `.*#NN.+` (number followed by ≥1 char) uniquely selects the pair row — whitespace-independent (don't match a literal " · " separator; a driver may normalize spaces). Pairs render in **insertion (image-completion) order = NON-deterministic** (`listPlaceholderPairs` returns raw `by_job` index order), so assert order-independently: re-anchor `scrollUntilVisible {direction: UP, text: "Matched pairs"}` before each number and scroll DOWN. (The 3 pair-text lines span a ~456px band < the 629px viewport, so they co-fit once scrolled to — but the re-anchor is the robust-against-taller-section insurance.)
- Crops: Maestro can't see `<img>`; the slot shows `"Loading image…"` then `"Image unavailable"` on failure. Assert absence of both.

## ConfirmDialog (shared, `components/modules/confirm-dialog.tsx`)
Close/Abort are guarded by a `role=dialog` confirm. Focus opens on **Cancel** (safe default), so the confirm is the 2nd button.
- Close → title `"Close this scan session?"`, confirm button **`"Yes, Close"`**.
- Abort → title `"Abort this scan session?"`, confirm button `"Yes, Abort"`.

## THE gotcha: resolverCalls is recorded ONLY by the FINAL pairing run
`resolverCalls` stays **0** all through "Collecting" even after the batch shows 6/6 + 3 pairs. The provisional/incremental pairing runs form the pairs but deliberately DON'T record the count (`placeholderPairing.ts` returns before `recordResolverCalls` unless `final`). In STREAM mode the final run fires only when the stream is CLOSED: `closePlaceholderStream` → `closeStreamImpl` (if `settled >= total`, status collecting→pairing + schedules `runPairing(final:true)`) → records `resolverCalls=6` (identity-first, `useAdjacency:false`, each done image resolved once = a dictionary lookup, not a model call) → `markJobSucceeded` (status "succeeded"). `recordResolverCalls` commits BEFORE `markJobSucceeded`, so once the status reads "Succeeded" the count is already final.
- **Any flow asserting `resolver calls: N>0` MUST tap `Close Session` + confirm `Yes, Close` first.** This is why `pipeline-pairs-uploaded-scans` failed on PR #180 (CI 32253624200) after the counter-race fix f9eb1da let it reach the `resolver calls: 6` assert — the flow never closed.
- The close→succeeded transition is Convex-internal (all images already done — NO BiRefNet/Vision here), so it's a 15s scheduled-chain settle, NOT the 400s external-compute wait the pipeline itself uses. See [[patterns_per_worker_data_isolation]] is unrelated; this flow uses its own per-user job, no shared set.

## Why "by image pool" (identity) vs "by scan order" (adjacency) — and the STALE-FIXTURE trap
The pipeline is identity-first: `placeholderPairing.ts runPairing` calls `pairBatch(..., {useAdjacency:false})`, so ALL done rows go through the identity pool (→ `resolver calls: N` = done-image count, e.g. 6), and only what the pool CANNOT place falls to `guardedAdjacencyFallback` (mechanism `adjacency` → "by scan order", confidence `side-only` → "front/back only", score 0). The pool (`lib/pairing/pool.ts`) only pairs a front↔back when they AGREE on player (surname-fuzzy ladder in `names.ts`: "BUEHLER" front ↔ "Walker Buehler" back) or team; a FRONT's cardNumber is DISCARDED (`poolCardFromIdentity`), so cross-side number match is impossible; the side-only pool fallback only fires when NEITHER card has any identity. So: **"by image pool" requires the front and back to share an extractable player name (or team).**
- **THE fixture trap (bit CI 32258989989):** the synthetic fixtures (`generate-placeholder-fixtures.py`, committed `ddd6120` 08-18 19:43) were built for the OLD adjacency-PRE-pass model — each FRONT carries exactly ONE word, the SURNAME (VORKLE/QUILLDEN/MOSSBAUM), and the BACK's prose blurb names only the GIVEN name (Grebble/Marcus/Teodor). The model extracts nothing usable from a lone-surname front and extracts the GIVEN name from the back, so the two sides share no name → pool can't match → EVERY pair renders "front/back only · by scan order". The identity-first rework (`1651ad0` 08-18 21:09) + the flow's "by image pool" assertions (`7a84a6b`, same minute) landed WITHOUT regenerating the fixtures. So `pipeline-pairs-uploaded-scans` Step 5 (`.*#17.*by image pool.*`) is UNSATISFIABLE with the current fixtures. The generator's header still documents the dead "resolver calls: 0 / adjacency" contract.
- **NOT a product bug / NOT a live-listing pairing regression.** The pairs are CORRECT (right front↔right back, via the guarded fallback); the pairing CODE works as designed. Real cards print the player name on the FRONT, so the surname-fuzzy rung matches them → "by image pool". Only the surname-only synthetic front defeats it.
- **DON'T "fix" it by flipping Step 5 to "by scan order"** — that makes the release gate assert the OPPOSITE of the identity-first feature it protects (R1/R2 violation). The real fix is to regenerate the fixtures so front & back extract a SHARED name — a committed-binary + model-nondeterministic change to validate, i.e. owner-coordinated, not a YAML tweak.
- **THE FIX applied (2026-08-19, uncommitted on the neo-170 branch):** `generate-placeholder-fixtures.py` now prints the SAME full name "Given Surname" on BOTH sides — `draw_front` renders `f"{given} {surname}"` (font 58, was lone surname font 96); `draw_back` heading is the full name (font 52) and `BACK_BLURB` leads with `"{given} {surname} joined…"`. Both sides → identical extractable name → pool matches (player exact/fuzzy) → "by image pool". Merely adding the surname to the BACK is NOT enough: the FRONT extracted NOTHING from a lone surname (proven: the fallback pair rendered the back's given name, and `guardedAdjacencyFallback` only pairs non-contradicting neighbours, so the front must have had no player), so the FRONT must carry the full name too. A 2-word front stays `textCount~2` << 5 so side classification is unaffected (verified: pipeline still 6/6, 0 unmatched, 3 pairs).
- **LOCAL VERIFICATION BLOCKER — the pairs-section scroll freezes the browser on failing-RAM hardware.** With the new fixtures the pipeline reaches "6 of 6 … 3 pairs" → Close → "Succeeded" → "resolver calls: 6" (all pass), then `scrollUntilVisible "Matched pairs"` (Step 5's first cmd) freezes Chrome (rapid swipes repaint 6 crop images → memory spike; the failure screenshot never writes = frozen browser). Reproduced 4×. This is LOCAL-ONLY: the original CI failure was at the LATER `#17…by image pool` assert, so CI clears "Matched pairs" fine. Do NOT loop runs chasing local green here — the crops run server-side (Cloud Run), so local Vite/browser is the only fragile part, and this laptop's RAM can't render the pairs section reliably. Verify "by image pool" via CI (adequate RAM) instead. "3 pairs + Succeeded + resolver calls: 6" does NOT distinguish pool from adjacency (identical summary) — only the per-pair label does, so CI's Step-5 assert is the real gate.

This flow needs the branch's neo-170 Convex backend. The worktree's local Vite (`apps/web/.env.local`) points at shared dev the shared dev deployment, which carries whatever's deployed to dev — NOT an open PR branch. So a local `test:e2e:pick` run exercises the WRONG backend; the authoritative reproduction is the PR's Convex-preview E2E gate. Don't `convex deploy` the branch to dev to work around this (disrupts shared infra; needs approval).

## Preprocess capacity + warm fan-out (load-bearing for ANY placeholder-timing flow)
`convex/preprocessCapacity.ts`: preprocess Cloud Run runs `container_concurrency=1`, so `max_instances` == total concurrent capacity. `PREPROCESS_MAX_PARALLELISM` MUST equal the same env's `preprocess_max_instances`. **dev + preview = 3** (var unset → `DEFAULT_PREPROCESS_MAX_PARALLELISM`), **prod = 20**. So the CI E2E preview gate runs parallelism **3** → a 6-image batch is **two waves of 3**, NOT one wave (the "maxScale=20 → one wave" figure is prod-only).
- `convex/placeholderBatch.ts warmupPreprocess`: at stream/batch START (`runAfter(0)` from `startPlaceholderStream`/`startPlaceholderBatch`) it fires `PREPROCESS_MAX_PARALLELISM` warm-ups **concurrently** — one per instance (conc=1) — warming ALL N instances the batch's own fan-out (also capped at N) will use. This is what prevents the "only 1 instance warm → wave-1 siblings cold-start" failure mode. Plus the page mount hook `useWarmPreprocess()` and (in CI) the preprocess smoke test warming the revision first = triple warming.
- **`warmingUp` FE flag (page.tsx ~348):** derived, no backend flag — true iff some image is `queued` AND none is `processing`/`done`/`failed`. Cold → shows "Warming up the card processor — this can take a minute on the first scan."; warm → never meaningfully appears.

## Two-phase wait pattern (replaced the single 400s blanket wait, commit 080bf13 on #180)
The flow's Step 3 is now TWO bounded `extendedWaitUntil`s on the SAME status line (both above the fold — Step 2 asserts it visible without scrolling):
- **Phase 1 (cold-start, 200000ms):** `.*[1-6] of 6 images processed.*` — engages when done≥1, NEVER matches "0 of 6" (the char before " of 6 images processed" is the done digit; "0"∉[1-6]). Verified with `re.fullmatch(..., re.IGNORECASE|re.DOTALL)` against composed strings: rejects 0/6, accepts 1/3/6, ignores sibling nodes (resolver/warming/image-summary). Absorbs the accepted ~191s model-load cold start.
- **Phase 2 (processing, 60000ms):** `.*6 of 6 images processed, 0 failed, 3 pairs.*` — the SLA guard; every number load-bearing; also catches a FAILED image (done increments but "0 failed" never matches → times out → fails, correctly). Holds <60s because from done=1 the instances are warm and only ~1 warm wave (3 images) remains: warm per-image ≈ classical fast-path ~1-2s or BiRefNet ~35s worst + Vision ~1-3s, so < 60s even worst case. **Residual risk for the CI gate:** if the 3-concurrent warm fan-out doesn't land before real dispatch AND Cloud Run cold-spins a wave-1 instance staggered from its siblings, that image's model load could exceed 60s — the design mitigates it, the preview gate confirms it. If a warm 6-image batch genuinely needs >60s, that's a product finding (pipeline not user-ready), NOT a timeout to bump.
